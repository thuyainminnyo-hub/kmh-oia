## 1. Standards basis

RFC 8493 states that BagIt 1.0 creation and validation tools MUST support SHA-256 and SHA-512, and SHOULD enable SHA-512 by default when creating new bags. It allows multiple payload manifests using different algorithms and recommends tag manifests use the same algorithms as the payload manifests.

Reference:
- https://www.rfc-editor.org/rfc/rfc8493.html

The Library of Congress `bagit-python` documentation states that SHA-256 and SHA-512 are generated by default and that validation reports checksum mismatch, missing payload files, and unexpected payload files.

Reference:
- https://github.com/LibraryOfCongress/bagit-python

## 2. Implementation update

The Gate A worker now requests both `sha256` and `sha512` manifests when creating a BagIt package. The independent intake receipt continues to record SHA-256 and byte length from source capture and staged-byte re-read. The receipt records both manifest algorithms and obtains the installed BagIt version through Python package metadata rather than relying on a possibly absent module constant.

The test suite now asserts that all four expected files exist:
- `manifest-sha256.txt`
- `manifest-sha512.txt`
- `tagmanifest-sha256.txt`
- `tagmanifest-sha512.txt`

It also asserts the receipt names both algorithms and contains a concrete package version. These assertions are committed but CI has not yet been inspected for this new commit.

## 3. Independent conformance plan

Run the LOC BagIt Conformance Suite for v1.0 separately from unit tests:
- valid fixtures must pass;
- invalid fixtures must fail;
- warning fixtures must be surfaced as warnings, not silently treated as clean;
- POSIX-specific invalid fixtures must fail on Linux;
- preserve exact fixture bytes and disable Git line-ending conversion for the fixture checkout.

Reference:
- https://github.com/LibraryOfCongress/bagit-conformance-suite

RFC 8493 also requires path handling to prevent manifest/fetch paths from accessing files outside the bag and recommends special-directory-character security tests. BagIt checksums provide integrity/corruption detection but are not authentication against active attackers. A future signed receipt requires a separate key custody and signature verification design.
