# Cybersecurity Remediation Executor Contract

**Status:** Implementation specification — no production executor is implemented by this document.  
**Applies to:** KMH OIA cybersecurity registry and `LiveRuntimeBridge`.  
**Release posture:** HOLD. The current bridge deliberately blocks cybersecurity remediation even when its registry guard returns allow.

## Objective

Define a narrow, typed boundary for a future asset-scoped remediation executor. Authorization and execution are separate decisions. A valid registry approval must never cause the generic OIA/LLM runtime to execute a security objective.

## Proposed request and result contract

The integration should use immutable, typed values (dataclasses or equivalent validated types), not free-form objective text as execution instructions.

A request must contain:
- `command_id`: the existing console command identifier.
- `case_id` and `registry_version`: the exact immutable registry record reference.
- `asset_id`: the canonical asset identifier from the approved record.
- `action`: one supported action (`mitigate`, `remediate`, `monitor`, or `escalate`).
- `approval_id`: an identifier for the exact approval evidence.
- `idempotency_key`: stable key to prevent duplicate side effects on retries.
- `requested_at`: timezone-aware timestamp supplied by trusted runtime code.

The executor result must include:
- `execution_id` generated by the trusted execution service.
- `command_id`, `case_id`, `registry_version`, `asset_id`, and `action` echoed from validated inputs.
- `executor_id` and the concrete execution environment/target identifier.
- `started_at` and `finished_at`, timezone-aware.
- `status`: a bounded enum such as `SUCCEEDED`, `FAILED`, `PARTIAL`, or `UNKNOWN`.
- references to before-state evidence, action transcript/result evidence, after-state evidence, and rollback evidence or an explicit reason rollback evidence is not applicable.
- a structured error code on failure; never include credentials or secret values.

An executor result is an observation, not independent proof of successful remediation. Do not mark the command `VERIFIED` based solely on `status=SUCCEEDED`.

## Mandatory execution sequence

1. Read and validate the exact registry case/version and complete hash chain.
2. Resolve command metadata through trusted application code. Do not derive case, asset, action, or approval from `command.objective`, caller-provided dictionaries, or untrusted free text.
3. Validate source verification, asset applicability, risk decision, owner, exact approval scope, approval validity window, rollback plan, and schema.
4. Bind the request to the approved `asset_id` and action. Reject any mismatch before side effects.
5. Resolve the executor from a trusted, startup-configured allowlist. Do not accept an executor supplied by a command or request.
6. The executor independently rechecks its own least-privilege asset scope immediately before side effects. Registry approval is not a substitute for runtime credentials or target-side authorization.
7. Persist a denial/start event before action where feasible; persist a completion/failure event with correlated IDs and evidence references afterward. Audit persistence failure must follow an explicit fail-closed policy for consequential actions.
8. Capture post-action state and run an independent verifier against the stated remediation criterion. Only the verifier may promote the result to verified; uncertainty or missing evidence remains `UNKNOWN`/HOLD.
9. On failure or partial execution, follow the approved rollback/escalation plan; record the rollback attempt and its independently verified outcome.

## Non-negotiable invariants

- No cybersecurity remediation command may fall through to `self.runtime.execute_detailed(command.objective)`.
- No executor call occurs on missing, invalid, expired, future-dated, pending, denied, out-of-scope, or tampered approval/evidence.
- No cross-asset or cross-action approval reuse.
- Retries must be idempotent or explicitly rejected when idempotency cannot be guaranteed.
- Denials and errors must not leak secrets into console output, logs, or audit events.
- A successful process exit or executor return is not equivalent to a verified security outcome.
- Keep non-security command behavior unchanged unless a separately approved policy says otherwise.

## Required tests before wiring an executor

- Missing guard, missing case/version, corrupt hash chain, schema-invalid record, unknown applicability, and decision `hold` all block with zero executor calls.
- Pending, expired, future-dated, incomplete, or denied approval blocks with zero calls.
- Wrong asset, wrong action, wrong approval scope, or non-allowlisted executor blocks with zero calls.
- Generic runtime spy remains uncalled for every cybersecurity command, including allowed authorization.
- Valid exact-scope approval invokes only the registered executor once with the approved asset/action and stable idempotency key.
- Executor exception, partial result, malformed result, and audit-store failure have explicit fail-closed behavior.
- Independent verifier failure leaves the result unverified and prevents learning/promotion.
- Rollback evidence is linked to the original execution and independently checked.
- Existing non-security bridge tests remain green.
- Integration tests exercise the real bridge-to-executor boundary using a fake, non-production executor; no live assets are touched by CI.
